# Address proximity UX contract

- UX-01: First focus of any Address field requests native foreground permission directly, including an empty field or an existing address. No app-launch prompt and no separate in-app location modal.
- UX-02: Native iOS purpose text: “Allow FieldSoli to use your location to suggest nearby addresses.” Android uses system permission wording. iOS defaults to reduced accuracy; Android excludes fine-location permission. No Always, motion, background-location or location foreground-service access is requested. The linked Expo Location module includes Core Motion APIs, so Apple's binary validation requires an `NSMotionUsageDescription` string even though the app does not call those APIs: “FieldSoli uses location services for nearby address suggestions. Motion and fitness data is not requested or collected.” Setting a purpose string does not request OS permission.
- UX-03: Denial and location/provider errors are silent. Manual editing, keyboard, drafts and suggestion selection retain existing behavior. Suggestions may initially be unbiased while location resolves, then refresh for the current query when a usable point arrives.
- UX-04: Privacy Choices order: Analytics, Device permissions, Legal, Delete Account. Device permissions uses the existing Account section typography and a ProfileRowsCard containing “Address suggestions” and “Contacts”, with no row subtitles, badges, or chevrons. All three settings use the same native Switch style. Device switches reflect OS permission: granted location or full/limited Contacts access is on; denied or not requested is off. Switches are disabled while reading permission status or opening Settings, and when status is unavailable. Limited Contacts access is described in the accessibility hint.
- UX-05: Tapping either device switch shows the native permission request only when that permission has never been requested. Later taps, whether access is on or off, open FieldSoli's app settings. iOS does not expose a supported link to the individual Location or Contacts pane, and does not show a permission's Settings control until the first native request. Switch values never change optimistically: refresh from the OS after the request and on foreground return. Expired one-time location grants follow the existing installation-level asked flag and route to Settings. Opening Privacy Choices itself never asks for permission, obtains a location fix, or reads contact data.
- UX-06: Existing legal gate asks for privacy version 2026-10-24; Terms and analytics controls retain their separate behavior. Neither privacy agreement nor analytics consent grants device-location permission.
- UX-07: Accepted October 24 platform constraint: retain separate Address suggestions and Contacts switches even though both subsequent actions use the same app-settings link. iOS may resume whichever permission subpage was last open. The app does not promise to select an individual permission or reset Settings navigation; the user accepted this behavior instead of adding a shared management action or extra guidance.

Use the local approved preview under docs/product/chatgpt/address-location-privacy-choices.html. It is a design reference, not native runtime evidence. Native text scaling, VoiceOver/TalkBack, focus and keyboard continuity remain release checks.
